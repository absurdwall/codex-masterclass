1. Codex CLI: work where the code lives

Use the CLI when the important context is already in a repository: source files, Git changes, test commands, and logs. It can inspect code, make edits, run tools, and continue a conversation in the terminal.

Example · understand before editing

Open a terminal in the project, start codex, and ask: “Explain how this service receives a request, where validation happens, and which tests cover it. Do not change files yet.”

Check the cited files. Then request one specific change, inspect the diff, and run the relevant tests. The CLI uses tools installed on its host; it does not supply every project dependency.

Configure authentication first using the official guide. ChatGPT sign-in and API-key sign-in are different access and billing paths. Model selection does not grant access to a model your account cannot use.

2. Non-interactive mode: one task, one useful output

codex exec fits repeatable reports, scripts, and CI. It normally writes progress to stderr and the final answer to stdout. The examples below use documented syntax and original teaching prompts; they have not been run against your repository.

Start with a read-only repository briefing

codex exec --sandbox read-only \
  "Map this repository's entry points and test commands. Do not change files."

Run it inside an authenticated, trusted Git repository. Check the reported entry points and commands against actual files. Non-interactive mode defaults to read-only; the flag makes that boundary explicit.

Save machine-readable progress

codex exec --sandbox read-only --json \
  "Identify the test framework and summarize the project layout." \
  > events.jsonl

--json produces a stream of JSONL events, not a single final JSON object. Your script must inspect failures and the result. The shell writes events.jsonl; a read-only agent sandbox does not prevent shell redirection.

When you need edits or a structured final answer

Use --sandbox workspace-write only when local edits are intended. Give a real bug description, limit the change, and require tests:

codex exec --sandbox workspace-write \
  "Add one regression test for the empty-input bug described in bug.md. Run the relevant test. Do not commit or push."

For a schema-constrained final answer, use --output-schema with a JSON Schema file. Keep publishing or merging separate from generating a proposed result. The older --full-auto flag is deprecated.

A script still needs a review boundary

Handle failure, cancellation, and partial output. Inspect diffs and test evidence before accepting a change. In CI, protect credentials and restrict repository permissions; do not expose secrets to untrusted build steps.

3. Developer commands: a reference, not another tool

The Developer commands page covers several surfaces. Read the section for the client you are actually using.

Shell commands

codex, codex exec, codex resume, and codex review are typed in a terminal.

Flags

--sandbox or --model configure a command invocation.

In-app commands

Slash commands such as /status, /model, and /review work in supported Codex composers. Desktop, CLI, and IDE lists differ; IDE command-palette actions are another surface.

ChatGPT web’s slash menu is separate. Pasting a CLI command into a normal chat does not execute it in your terminal.

4. Agents API: put an agent into your application

Use the Agents API when your service needs to submit work, retain a session, observe progress, and continue later. OpenAI manages the Codex harness, including orchestration, compaction, and recovery. Your application still defines instructions, tools, access, and the execution environment.

Integration idea · bug investigation service

A user submits a bug report. Your service creates an agent session, stores its ID with the issue, displays progress, and returns a reproduction and proposed fix for review. Follow-up information goes to that same session.

The product must handle failures and cancellation, protect repository access, and separate a proposed fix from approval to merge.

Know which API layer you need

InterfaceWho runs the agent orchestration?
Agents APIOpenAI manages the Codex harness and durable sessions
Agents SDKYour application runs orchestration using the SDK’s agent, tool, and handoff abstractions
Responses APIYou integrate model responses and tools directly, with more control over the surrounding application

The Agents API is currently beta and requires Platform setup and suitable API access. It is not included merely because you have a ChatGPT subscription. Budget for the whole task, including model calls, tools, retries, and environment use.

A minimal integration checklist
  1. Define readable sources, allowed tools, and actions needing human approval
  2. Choose an OpenAI-hosted or appropriate self-hosted environment and its network policy
  3. Create the session and store its ID with your application’s work item
  4. Consume events and inspect completed output; a finished turn does not prove every tool succeeded
  5. Continue the same session when needed; after a disconnected stream, recover saved state/items instead of assuming events replay

Follow the current quickstart for beta headers and credentials. Keep API keys outside the agent sandbox and out of public source code.
