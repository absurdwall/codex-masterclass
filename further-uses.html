MCP Events: “something happened” can start the work

A time trigger

“Every weekday at 8:00, check the release notes.” The scheduled time arrives, then the task checks.

An event trigger

“When a relevant PR review arrives, assess it.” The app sends an event; a configured subscription can start the task.

MCP Events lets a connected app notify the assistant when something happens. A developer sets up the supported events and the webhook that delivers them. Tools let the agent act; events tell it when to look. Available events depend on the connected server.

Follow an issue from report to reviewed fix

Conceptual custom-plugin example: GitHub issue created → custom MCP event → dot reads the issue and project Page → bounded Cloud task investigates and tests → draft PR, if authorized → human review → material project-state update → next action.

This needs an MCP server that advertises an issue-created event, repository access, a published Cloud environment, and explicit instructions for edits and PRs. The built-in GitHub trigger currently documents PR activity, not issue creation. For a built-in example, begin with a PR review/comment or commit update instead.

An event does not authorize a merge. Fetch the source, check relevance, avoid duplicates, and stop for review.

Which event route is available?
  • Built-in event-triggered tasks: supported Gmail, Slack, and GitHub events on eligible web/mobile accounts. A task cannot combine an event trigger with a time schedule.
  • Custom MCP Events: documented for Work web, desktop Work using Cloud, and dots. A developer must set up a server that supports events and webhooks.

Before a demo, check which events your account and server support, then create the subscription.

1. Codex CLI: work where the code lives

Codex CLI is the terminal app. Use it when your source files, Git changes, test commands, and logs are already in a repository. It can inspect code, make edits, run tools, and continue a conversation in the terminal.

Example · understand before editing

Open a terminal in the project, start codex, and ask: “Explain how this service receives a request, where validation happens, and which tests cover it. Do not change files yet.”

Check the cited files. Then request one specific change, inspect the diff, and run the relevant tests. The CLI uses tools installed on its host; it does not supply every project dependency.

Sign in first using the official guide. ChatGPT sign-in and API-key sign-in are different access and billing paths. Model selection does not grant access to a model your account cannot use.

2. Non-interactive mode: one task, one useful output

codex exec runs one defined job without an interactive conversation. Use it in a script or automated code check. It sends progress to the error/progress stream (stderr) and the final answer to the normal output stream (stdout). The examples below use documented syntax and original teaching prompts; they have not been run against your repository.

Start with a read-only repository briefing

codex exec --sandbox read-only \
  "Map this repository's entry points and test commands. Do not change files."

Run it inside an authenticated, trusted Git repository. Check the reported entry points and commands against actual files. Non-interactive mode defaults to read-only; the flag makes that boundary explicit.

Save machine-readable progress

codex exec --sandbox read-only --json \
  "Identify the test framework and summarize the project layout." \
  > events.jsonl

--json writes one JSON event per line (JSONL), so a script can follow progress. It is not one final JSON object. Check failures as well as the result. The > in this example writes events.jsonl, even though the agent itself is in read-only mode.

When you need edits or a structured final answer

Use --sandbox workspace-write only when local edits are intended. Give a real bug description, limit the change, and require tests:

codex exec --sandbox workspace-write \
  "Add one regression test for the empty-input bug described in bug.md. Run the relevant test. Do not commit or push."

For a final answer in a fixed format, use --output-schema with a JSON Schema file. Keep publishing or merging separate from generating a proposed result. The older --full-auto flag is deprecated.

A script still needs a review boundary

Handle failure, cancellation, and partial output. Inspect diffs and test evidence before accepting a change. In CI, protect credentials and restrict repository permissions; do not expose secrets to untrusted build steps.

3. Developer commands: a reference, not another tool

Read the Developer commands section for your app: desktop, CLI, or IDE.

Shell commands

codex, codex exec, codex resume, and codex review are typed in a terminal.

Flags

--sandbox or --model set options for the command you run.

In-app commands

Slash commands such as /status, /model, and /review work in supported Codex composers. Available commands differ between desktop, CLI, and IDE. An IDE also has its own command palette.

ChatGPT web’s slash menu is separate. Pasting a CLI command into a normal chat does not execute it in your terminal.

4. Agents API: put an agent into your application

Use the Agents API to let your application start a task, show its progress, and continue the same work later. OpenAI runs the agent and keeps the session. You still choose its instructions, tools, permissions, and where it runs.

Integration idea · bug investigation service

A user submits a bug report. Your service creates an agent session, stores its ID with the issue, displays progress, and returns a reproduction and proposed fix for review. Follow-up information goes to that same session.

The product must handle failures and cancellation, protect repository access, and separate a proposed fix from approval to merge.

Know which API layer you need

InterfaceWho manages the agent’s work?
Agents APIOpenAI runs the agent and saves sessions so work can continue
Agents SDKYour application coordinates agents, tools, and handoffs using the SDK
Responses APIYour application calls the model and tools directly, giving you more control over how they fit together

The Agents API is in beta. It requires Platform setup and API access; a ChatGPT subscription alone does not include it. Budget for model calls, tools, retries, and environment use.

A minimal integration checklist

OpenAI’s Codex harness coordinates the agent’s steps, condenses long conversation history (compaction), and recovers interrupted work.

  1. List the sources the agent can read, tools it can use, and actions needing human approval
  2. Choose an OpenAI-hosted or appropriate self-hosted environment and its network policy
  3. Create the session and store its ID with your application’s work item
  4. Read progress events and check the result; a finished turn does not prove every tool succeeded
  5. Continue the same session when needed. If the connection drops, retrieve saved state and items; do not assume missed events will replay

Follow the current quickstart for beta headers and credentials. Keep API keys outside the agent sandbox and out of public source code.
