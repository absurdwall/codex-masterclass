Topic 04 · Detailed reading

Dots & Space: the practical guide

What to delegate, where work happens, and how to keep a result useful and safe to share.

In the sessionDetailed reading guide

Start with one responsibility, a review point, and a place for the result. This guide uses a fictional workshop plan to show the full workflow, then applies the same pattern to a coding task.

Where each shines, and one useful trick

dot: keep a multi-step task moving

Useful when work involves several sources, a few drafts, and decisions along the way. Give it an outcome and a review point, then refine the assignment in the same conversation.

Try: “Keep a shortlist from these proposals. Bring me the decisions that block progress, with your recommendation and evidence.”

Space: improve a document in context

Useful when the result needs edits, feedback, and a lasting home. Select the passage that needs work or leave a focused comment, rather than asking for an unnecessary full rewrite.

Try: “Rewrite only this paragraph for a first-time reader. Preserve the rest of the Page.”

For either product, make the next result easy to inspect: a comparison, a changed paragraph, a tested fix, or a clear decision. Keep the best result in a Page with its evidence and next action.

1. Delegate an outcome, not just a question

“Explain the options” and “Help me get this decision made” are different assignments.

A dot can continue work between conversations and bring back results or decisions that need you. You can add information or change priorities while it works. Ordinary ChatGPT can also use tools and handle multi-step tasks; the useful distinction here is ongoing responsibility and follow-through.

Immediate request

“Compare these proposals and explain the trade-offs.” You want analysis now.

Ongoing responsibility

“Help me prepare the workshop. Track unresolved decisions and tell me about changes that affect the plan.” You want continuing coordination.

A schedule adds an explicit trigger. A Page gives the output a durable home. Neither is automatically created just because you asked a dot for help.

2. Check access and where the task will run

Start on a supported desktop app or desktop web surface and check your account’s available features. Connect only the accounts and sources relevant to the work. Then identify the execution environment explicitly.

3. Write a brief the agent can finish

This is a teaching checklist, not special syntax. Include the fields that affect the result.

  • Outcome: What should exist when the work is finished?
  • Sources: Which actual files, Pages, sites, or connected channels should it use?
  • Scope and authority: What may it change or send? What needs your review?
  • Timing: One task, ongoing follow-through, or a saved recurring schedule?
  • Delivery and evidence: Where should the result appear, and how will you check it?
Example brief · fictional workshop

Help me prepare the 24-person design workshop on 18 November. Use the attached brief and three venue proposals. Compare total cost, capacity, accessibility information, and cancellation terms. Save a recommendation and source links in a Workshop planning Page. Label unknowns. Prepare questions for my review; do not contact venues or make a booking. Finish when the comparison and unresolved questions are ready.

The stop condition makes this a bounded assignment. For recurring checks, specify the cadence and end date; for supported event monitoring, specify the event and stopping condition.

4. Keep continuity, but verify important details

A dot can use relevant preferences and ongoing context. That does not guarantee perfect recall or mean a newly delegated task receives every previous conversation. Repeat a critical constraint or point to its authoritative source.

Proactive help may draw on connected information. Review which account you connect and correct outdated assumptions plainly: “The capacity requirement is now 24.” Save important decisions in the project Page as well, where others can inspect them.

Watch the actual work

Use Activity to inspect progress, outputs, and requests for input. Review Scheduled separately for recurring tasks. Pausing the dot, stopping a delegated task, and canceling future scheduled runs have different effects.

Access and authorization are separate. Being able to read an app does not grant permission to send messages from it. A completed status is a reason to inspect the result, not proof that every acceptance check passed.

5. Give the result a home in Space

ChatGPT Space brings saved Pages, files, and shared work together. A space groups related material. A Page is an editable document and can have child pages. Your account’s workspace determines membership and settings.

Projects remain separate: they organize chats, files, and project instructions. Space does not replace Projects. Saving a Page also does not make it automatically update or become the dot’s complete memory.

A useful document structure

Workshop planning

  • Overview Page: current decision, owner, next action, and last-reviewed date
  • Venue comparison: evidence, source links, assumptions, and unknowns
  • Agenda and notes: the working schedule and meeting record

A reader should be able to find the recommendation and challenge its evidence without reconstructing the original chat.

Choose the right editing interaction

  • Explore a change: use the conversation beside the Page and specify whether you want advice or an edit
  • Revise a passage: select text and use Ask for change where available
  • Request work in context: mention @ChatGPT or select your dot from the @ menu, inline or in a comment
  • Ask a colleague: mention the intended collaborator in a focused comment
Example Page comment

@dot Compare the capacity claims in the three linked proposals. Add a discrepancy note under Venue comparison. Preserve the existing recommendation until I review it.

Open the affected section after the response. Pages can combine headings, lists, tables, images, files, and interactive visualizations; use only what helps the next reader. A reusable Prompt block is a starting request, not a recurring schedule.

6. Review the audience before sharing

Use the narrowest suitable available role: view for reading, comment for feedback, edit for co-authorship. Available roles and recipients depend on the account and workspace.

  • Parents matter: sharing a space includes its Pages; sharing a Page includes its child pages. Removing a direct invitation may leave inherited access intact
  • Links and copied content differ: a linked external file keeps its original access rules. Information copied or summarized onto a Page becomes visible to that Page’s readers
  • Inspect the actual artifact: uploaded files follow Page permissions. Private chats and saved memory are not automatically shared, but their contents may have been copied into the Page

Check the Page and its children, then confirm the recipient can open the result and any necessary source links.

7. Walk through a decision from start to finish

  1. Prepare comparable inputs

    Provide the workshop brief and three proposals. Identify taxes, fees, and missing accessibility details rather than treating different quotes as equivalent.

  2. Delegate the comparison

    Use the brief above. Request a recommendation with evidence beside material claims and an explicit list of unknowns.

  3. Save and inspect

    Create the decision Page and its comparison child page. Verify capacity, dates, calculations, and cancellation terms against the original proposals.

  4. Invite the reviewer

    Choose appropriate access. Check that sharing the child comparison is intentional and that external links work for the recipient.

  5. Approve the next action

    Decide whether to contact a venue or book. The earlier research brief authorized preparation, not either of those actions.

  6. Maintain only if useful

    For a Monday review until the decision deadline, explicitly request a schedule. Verify its saved instructions, time zone, destination, enabled state, and first result.

8. Apply the same pattern to code

Example · a reviewable bug fix

Investigate the mobile checkout failure in the named repository using the configured Codex cloud environment. Reproduce the bug, prepare the smallest justified fix, and run relevant tests. Provide a reviewable diff plus evidence of the original failure and corrected behavior. Do not merge or deploy. Put the issue summary, test results, and unresolved risks in the Release readiness Page.

The repository and environment are the working context. The diff and tests are the technical evidence. The Page is the human-readable record. Check each deliverable; a finished task label does not prove a test ran or a deployment succeeded.

Before your first real task

  • Can you name the desired result and its stop condition?
  • Does the agent have the actual sources and the right execution environment?
  • Is the boundary between preparation and action explicit?
  • Can you verify the output and the people who can see it?
  • If it repeats, can you find the saved schedule and inspect a run?

Availability varies by account, region, client, and workspace. At launch, Space Page editing is documented for web and desktop; mobile supports finding, reading, and sharing Pages. Check the current Space guide before planning a phone-only exercise.
