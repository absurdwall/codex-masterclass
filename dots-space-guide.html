Topic 04 · Detailed reading

Dots & Space: the practical guide

What to delegate, where work happens, and how to keep a result useful and safe to share.

In the sessionDetailed reading guide

Give your dot a clear job, check its work, and keep the latest result in a Page. The examples below follow a fictional workshop and a code release.

Where each shines, and one useful trick

dot: keep a multi-step task moving

Use a dot for work with several sources, drafts, and decisions. Give it a goal and a review point, then refine the task in the same conversation.

Try: “Keep a shortlist from these proposals. Bring me the decisions that block progress, with your recommendation and evidence.”

Space: improve a document in context

Use Space for a document you’ll edit, review, and return to. Select a passage or leave a focused comment to change just that part.

Try: “Rewrite only this paragraph for a first-time reader. Preserve the rest of the Page.”

Ask for a result you can check: a comparison, a changed paragraph, a tested fix, or a decision. Save it in a Page with the evidence and next action.

1. Decide what the assistant owns

A Scheduled Task runs at a set time or event. Give a dot the broader goal and the work needed to reach it.

A task that runs on a trigger

“At 9 AM each Monday, compare the three linked proposals with last week’s summary and report material changes.” A Scheduled Task runs the saved instructions at the requested time.

Each run can reason and use tools and available context. Specify its sources, expected result, and when it should stop.

An ongoing responsibility

“Help get the workshop ready by 18 November. Track the unresolved decisions and bring me a recommendation when new information changes the plan.” A dot can carry the goal and next steps across conversations.

It can delegate Work or Codex tasks, check results, and plan the next step.

You can combine them: the dot coordinates the workshop and uses the saved Monday check. A supported app event can also trigger a saved task. Verify that any requested schedule or event trigger was actually created.

Set limits: what the dot may do, what needs your decision, and when the job ends. Use a simple chat for a one-off comparison.

2. Check access and where the task will run

Check which features your account supports in the desktop app or desktop web. Connect the sources needed for the task, then choose where it will run.

3. Write a brief the agent can finish

Use the parts of this checklist that matter for your task; no special syntax is needed.

  • Outcome: What should exist when the work is finished?
  • Sources: Which actual files, Pages, sites, or connected channels should it use?
  • Allowed actions: What may it change or send? What needs your review?
  • Timing: One task, ongoing follow-through, or a saved recurring schedule?
  • Delivery and evidence: Where should the result appear, and how will you check it?
Example brief · fictional workshop

Help me prepare the 24-person design workshop on 18 November. Use the attached brief and three venue proposals. Compare total cost, capacity, accessibility information, and cancellation terms. Save a recommendation and source links in a Workshop planning Page. Label unknowns. Prepare questions for my review; do not contact venues or make a booking. Finish when the comparison and unresolved questions are ready.

This brief says when the task is finished. For recurring checks, add how often to run and when to end. For supported event monitoring, name the event and when to stop.

4. Keep continuity, but verify important details

A dot can use relevant preferences and past context, but it won’t recall everything perfectly. A delegated task does not receive every previous conversation. Give it the current project Page, source files, and key constraints.

A dot may use connected accounts to offer help. Check which account you connect and correct outdated information: “The capacity requirement is now 24.” Save important decisions in the project Page so others can check them.

Watch the actual work

Check Activity for progress, results, and requests for input. Check Scheduled for recurring tasks. Pausing the dot, stopping a delegated task, and canceling future scheduled runs have different effects.

Permission to read an app does not include permission to send messages. When a task says it is complete, check that the result meets your requirements.

5. Keep a current project Page in Space

Space keeps working documents and files you can return to. A space groups related material; a Page is an editable document that can have child Pages. Keep the latest decisions, open questions, and next steps here for people and agents to read.

Use chats and Projects for discussion and reference material, Work and Codex to run tasks, and GitHub for code and its history. Keep a readable project summary in Space: what is true now, why, and what happens next. The Page doesn’t replace the repository or carry messages between agents.

Reusable project Page structure · adapt the headings

Workshop planning

  • Overview: purpose, owner, scope, and links to the brief and source files
  • Current state: what is ready, what is blocked, next action, and last-reviewed date
  • Decisions: the choice, who approved it, the reason, date, and supporting evidence
  • Open questions: what remains unknown, who can answer, and when it matters
  • Experiments: what you tried, what happened, and what that changes; link detailed results
  • Instructions: stable constraints and the steps the next task should follow
  • Milestones: target dates, owners, acceptance checks, and current status

Start with these sections in one Page. Move a long comparison or experiment log into a child Page when that makes the current state easier to scan.

Before and after each task

  1. Resume from the Page

    Link the Page in the next task. Ask the agent to summarize the goal, constraints, open questions, and next action. Correct anything outdated before work starts.

  2. Make progress in the right place

    Discuss the plan in chat or run the task in Work/Codex. Keep evidence in its original proposal, test result, issue, or pull request.

  3. Save what changed

    Update the Page after a decision, experiment, milestone, changed constraint, or resolved blocker. Link the evidence and replace outdated text. Date decisions when the history matters.

Reusable request · update after meaningful progress

Read the linked project Page before starting. Use its current state, instructions, and source links; flag anything stale or conflicting. After the work, update only the affected sections with the material result, evidence links, decisions, remaining questions, and next action. Preserve other contributors’ edits. Keep routine progress chatter in this conversation. Tell me what changed on the Page so I can review it.

“Space is where the project remembers” describes this saved-and-updated workflow. Saving a Page does not keep it up to date or include it in every task. It is not the dot’s complete memory. Check each edit and link the Page in the next brief.

Choose how to edit

  • Explore a change: use the conversation beside the Page and specify whether you want advice or an edit
  • Revise a passage: select text and use Ask for change where available
  • Request work in context: mention @ChatGPT or select your dot from the @ menu, inline or in a comment
  • Ask a colleague: mention the intended collaborator in a focused comment
Example Page comment

@dot Compare the capacity claims in the three linked proposals. Add a discrepancy note under Venue comparison. Preserve the existing recommendation until I review it.

Open the affected section after the response. Pages can combine headings, lists, tables, images, files, and interactive visualizations; use only what helps the next reader. A reusable Prompt block is a starting request, not a recurring schedule.

6. Review the audience before sharing

Choose the access people need: view to read, comment to give feedback, or edit to write together. Available roles and recipients depend on your account and workspace.

  • Check parent access: sharing a space includes its Pages; sharing a Page includes its child pages. Removing a direct invitation may leave inherited access intact
  • Links and copied content differ: a linked external file keeps its original access rules. Information copied or summarized onto a Page becomes visible to that Page’s readers
  • Check what the Page contains: uploaded files follow Page permissions. Private chats and saved memory are not automatically shared, but their contents may have been copied into the Page

Check the Page and its children, then confirm the recipient can open the result and any necessary source links.

7. Walk through a decision from start to finish

  1. Prepare comparable inputs

    Provide the workshop brief and three proposals. Identify taxes, fees, and missing accessibility details rather than treating different quotes as equivalent.

  2. Delegate the comparison

    Use the brief above. Request a recommendation with sources beside important claims and a list of unknowns.

  3. Save and inspect

    Create the project Page with its current state, recommendation, unresolved questions, and a link to the comparison. Verify capacity, dates, calculations, and cancellation terms against the original proposals.

  4. Invite the reviewer

    Choose appropriate access. Check that sharing the child comparison is intentional and that external links work for the recipient.

  5. Approve the next action

    Decide whether to contact a venue or book. The earlier research brief authorized preparation, not either of those actions.

  6. Update the state and plan the next check

    After a decision or new evidence, update the Page’s current state and next action. For a Monday review until the deadline, request a schedule. Check its instructions, time zone, destination, that it is enabled, and its first result.

Launch detail: Keep Updated

As checked on 1 October 2026, Keep Updated is unavailable at launch. Recurring updates need a separately confirmed saved task; writing the request on a Page does not create one.

8. Apply the same pattern to code

Example · a reviewable bug fix

Read the Release readiness Page for the current goal, constraints, and open questions. Investigate the mobile checkout failure in the named repository using the configured Codex cloud environment. Reproduce the bug, prepare the smallest justified fix, and run relevant tests. Provide a reviewable diff plus evidence of the original failure and corrected behavior. Do not merge or deploy. Update the Page’s current state, experiment result, remaining risks, and next action; link the code change and test evidence.

Codex does the work; the repository and GitHub history keep the code. The Page explains what the result means for the release. For example: “Mobile reproduction fixed; regression tests pass; checkout review still pending.” Include the relevant code version and evidence links so this state can be checked.

The dot can coordinate the investigation and next steps. Give the updated Page to the next task. Check the diff, test evidence, and Page edit separately before treating the work as complete.

Before your first real task

  • Can you name the desired result and its stop condition?
  • Does the agent have the sources and the right computer or workspace?
  • Is the boundary between preparation and action explicit?
  • Can you verify the output and the people who can see it?
  • Does the project Page show what changed, with evidence and a next action?
  • If it repeats, can you find the saved schedule and inspect a run?

Availability varies by account, region, client, and workspace. At launch, Space Page editing is documented for web and desktop; mobile supports finding, reading, and sharing Pages. Check the current Space guide before planning a phone-only exercise.
