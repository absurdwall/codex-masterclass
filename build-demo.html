Delegate the implementation

Codex Cloud: send a prepared job to a separate workspace

Local Codex feels like a pair programmer beside you. Cloud Codex feels like an engineer you brief, then review.

These are working styles, not different levels of intelligence. Local work is useful when you are iterating with your own files and apps. Cloud work is useful when a well-scoped task can run with a prepared repository and tools, while you do something else.

  • Longer work: delegate a bounded job and return to its result.
  • Parallel work: separate tasks can explore independent changes without editing the same working files.
  • Consistent setup: reuse a tested preparation instead of rebuilding the tools for every assignment.

The reusable environment

A prepared starting point: repositories, dependencies, tools, setup instructions, and access configuration. Publish it once, then reuse it for new tasks.

The task workspace

Each new task gets its own isolated workspace from that preparation. Task A’s edits do not appear automatically in Task B.

Prepared environmentRepository + tools + tested setup + allowed access
↓
Task AIts own files and changes
Task BIts own files and changes
Task CIts own files and changes

Reuse the preparation, not one mutable computer. Review and integrate task results deliberately through diffs and Git. A task’s edits do not rewrite the reusable environment.

Prepare it once, then check one fresh task
  1. In a new Codex task, choose Work in → Cloud → Select environment → Create environment and select the intended repositories.
  2. Prepare dependencies, tools, and required access. Review the setup report and test commands. The editor includes Install script and Start skill fields.
  3. Save and Publish. Wait for Environment published before starting a fresh task.
  4. After changing the setup, save and republish. New tasks use the new preparation; existing tasks retain their state.

Environment sharing determines who can use the setup. Keep credentials in supported access settings, not public exercise files.

Example · a small personal tracker

“Build a local page where I can add a task, mark it complete, and filter unfinished tasks. Use sample data. Keep the first version to one screen. Verify that adding, completing, filtering, and reloading behave as specified.”

Specify persistence

If information must survive a reload or be shared across devices, say so. A good-looking interface does not prove that the underlying data is saved correctly.

Computer use: observe → act → check

Computer use lets an agent interact with graphical apps through their interface. It is useful when the task depends on visible UI behavior or when a structured integration is insufficient. Because it can change app state, keep the task bounded and review access prompts.

  1. Observe the current state.

    Read what is actually on screen: the active app, current hand, legal choices, and whose turn it is.

  2. Choose one allowed action.

    Use the rules and visible state. If the state is unclear, inspect again rather than guessing.

  3. Act and inspect the result.

    Did the click register? Did the game advance? Is the expected card or result visible?

  4. Stop at the agreed boundary.

    A bounded demo should end after one hand, a time limit, or an unexpected condition.

A safe card-game demonstration

Example instruction · adapt to the selected app

“In this free, non-wagering practice game, play one hand using the visible rules. Explain each choice briefly. Stop if the rules or state are unclear, a purchase or login is required, or the hand ends. Report the result and anything you could not verify.”

What the audience should watch

  • Whether the agent reads the current state
  • Whether its action is legal
  • Whether it checks what changed
  • Whether it respects the stopping condition

What success means

A legal, observable sequence with a verified result. Winning is not required to demonstrate reliable computer use.

Scheduled tasks: save a job to run later

Scheduled Tasks specify when work runs. A Dot owns what needs to keep moving. Use a schedule for a defined repeatable job; use a dot to carry an ongoing goal, context, and follow-up decisions. A dot can coordinate scheduled checks as part of that responsibility.

A scheduled task keeps the instructions for a job and starts it at a future time or on a recurring schedule. It can do useful work, such as checking sources and preparing a report, rather than only reminding you to do it.

1. Describe the job

Say what to check, when to run, the time zone, and where the result should appear.

2. Try it once

Inspect a sample result. Tighten the sources and output before repeating it.

3. Verify the saved task

Open Scheduled on web or desktop. Check its instructions, timing, enabled state, and first run.

The schedule does not supply the computer

Local project tasks need that computer on and the app running. Cloud tasks use accessible uploaded context or connected tools; they cannot directly read an arbitrary folder on your laptop.

Connect it to the card-game demonstration

First verify one free, non-wagering practice hand manually. To repeat it later, keep the same game, environment, rules, and stopping condition, and add an explicit time and time zone. Stop and report if the app or game state is unavailable.

A “completed” run is not proof of a correctly played hand. Check the actions and result, including any reported blocker.
